# Инструкции по работе с проектом

## Общие правила
- Проект посвящён cозданию виджета клиента крупного банка на Python (см. README.md)
- Весь код должен соответствовать условиям задач
- Код должен быть понятным, но лаконичным

## Стиль кода
- Использовать русские комментарии и docstrings, как в исходном коде
- Соблюдать PEP 8, но не жертвовать ясностью ради формальностей
- Функции должны иметь информативные имена

## Подход к проверке кода
- При анализе кода сначала проверять логическую корректность
- Затем обращать внимание на соответствие требованиям задачи
- Комментировать только значимые моменты, избегать избыточных пояснений
- В тестах предпочитать конкретику: явные проверки значений и типов

## Особенности проекта
- Используются различные библиотек, такие как os, random, sys, datetime, time, json, requests, re,   `random` (функция `choice`)
- Работа с генераторами и декораторами
- Для некоторых функций входные данные могут быть в формате JSON

## Работа с файлами при проверке кода
При проверке кода:
- Всегда использовать команду `git diff` для актуализации знания о коде
- Избегать инструмента `read file` — он может возвращать экранированную строку вместо реального кода
- `git diff HEAD` позволяет видеть текущее состояние изменений без повторного чтения файлов

## Особенности инструмента read_file
- Инструмент `read file` может некорректно отображать содержимое файлов
- Он может возвращать экранированные символы (`\n` вместо реальных переносов строк)
- Для проверки кода всегда предпочтительнее использовать `git diff HEAD`
- Если `read file` показывает код с `\n` и другими экранированными символами — это его ограничение, а не реальное содержимое файла

## Особенности работы с этим файлом (.gigacode/instructions.md)
- При любом дополнении или редактировании файла сохранять его наглядную структуру
- Каждый новый пункт добавлять как отдельный блок с заголовком уровня ##
- Не объединять пункты в одну длинную строку
- Использовать пустые строки между секциями для лучшей читаемости

## Порядок действий при проверке кода
- При чтении кода сначала проверять его через `git diff HEAD`
- Если код не сохранён в репозитории, сначала сделать `git add <файл>` для создания начальной версии
- Только затем использовать `git diff HEAD` для анализа изменений
- Избегать инструмента `read file` — он может возвращать экранированную строку вместо реального кода
